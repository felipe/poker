## medium: Mandatory pre-merge gate falls back to an npm test command this repo does not have

id: fnd_sig-feat-config-9c89bf110d-5bfa2_0f3d87aa77
category: build-release
confidence: high
triage: risk
status: open
feature: Repository Basics (feat_config_9c89bf110d)

evidence:
- README.md:3
- README.md:147-151
- AGENTS.md:38-40
- commands/pre-merge.md:19-23
- commands/pre-merge.md:86-90

The current tree has no package.json and no .pre-merge.yml, so the mandatory /pre-merge workflow enters the fallback path. That fallback runs an npm test script, but the repository explicitly documents package-less tests via Node's built-in runner. A contributor or agent following the required gate will fail before running the real tests or need to override the documented workflow, making release readiness non-deterministic.

recommendation:
Add a root .pre-merge.yml that defines the unit stage as `node --test test/*.test.js` and reflects that there is no package manager/build step. Optionally adjust the fallback docs to handle package-less Node projects.

test analysis:
The unit tests validate app behavior when invoked directly; they do not validate that the mandatory pre-merge workflow can discover and run the correct command.

suggested regression test:
Run `/pre-merge` or an equivalent manifest-driven CI check and assert it executes `node --test test/*.test.js` successfully.

minimum fix scope:
Add .pre-merge.yml with the documented unit test command.

repro:
Repository scan found no package.json and no .pre-merge.yml. Following commands/pre-merge.md without a manifest reaches the fallback unit stage `npm test -- --run`, while the documented passing command is `node --test test/*.test.js`.

## medium: Simulation accepts invalid inputs that crash or return non-finite odds

id: fnd_sig-feat-library-64e37fe4c9-d55d_3436a9b413
category: api-contract
confidence: high
triage: contract-mismatch
status: open
feature: Simulation Engine (feat_library_64e37fe4c9)

evidence:
- js/simulate.js:33-43 (simulate)
- js/simulate.js:51-53 (simulate)
- js/simulate.js:70-72 (simulate)
- js/simulate.js:83-86 (simulate)
- js/variants.js:56-63 (maxPlayersForVariant)

simulate is an exported library entrypoint taking user-controlled variant, opponent count, revealed cards, and iteration count, but it does not validate the variant key, non-negative card requirements, deck capacity, or positive iterations. Impossible but representable inputs violate the documented SimResult contract: a too-large seven-card stud simulation deals past the deck and crashes in evaluate with an undefined card, an unknown variant throws a raw TypeError, and iterations=0 returns NaN for winRate and every distribution entry. variants.js shows deck capacity is known, but that invariant is not enforced at the simulation boundary.

recommendation:
Validate at the start of simulate: require a known variant, finite integer iterations > 0, finite non-negative integer numOpponents, revealed counts within the variant limits, no duplicate cards, and cardsNeeded <= remaining.length. Throw a clear RangeError/TypeError or return an explicit failure shape before entering the shuffle loop.

test analysis:
test/simulate.test.js only exercises valid variant names, positive iteration counts, and opponent counts within deck capacity. The shape test asserts 0..1 only for a positive 200-iteration Hold'em run.

suggested regression test:
Add simulate tests for iterations=0, unknown variant, and sevenstud with more opponents than maxPlayersForVariant("sevenstud") - 1, asserting clear validation errors instead of NaN or raw TypeError crashes.

minimum fix scope:
js/simulate.js input validation plus focused tests in test/simulate.test.js.

repro:
node --input-type=module -e 'import {simulate} from "./js/simulate.js"; console.log(simulate([], [], 10, "sevenstud", 1))' throws TypeError: Cannot read properties of undefined (reading 'rank'). node --input-type=module -e 'import {simulate} from "./js/simulate.js"; console.log(simulate([], [], 1, "holdem", 0))' returns NaN values.

## medium: Vegas Neon removes visible focus from action buttons

id: fnd_sig-feat-config-98482e6221-7662d_9a1cc9a266
category: bug
confidence: high
triage: confirmed-bug
status: open
feature: Theme System (feat_config_98482e6221)

evidence:
- index.html:80-85 (#deal, #play, #fold)
- themes/vegas-neon.css:182-186 (select:focus, button:focus)

The Vegas Neon theme suppresses the browser focus outline for every button, but the replacement focus styling that follows is only applied to selects. Deal, Play, and Fold are keyboard-focusable buttons, so keyboard users can tab onto the primary game controls without any visible focus indicator in this theme.

recommendation:
In themes/vegas-neon.css, either stop clearing button outlines or add an explicit button:focus-visible style, for example a neon cyan outline/box-shadow with outline-offset. Keep the existing select focus styling.

test analysis:
The existing node --test test/*.test.js suites passed 119/119, but they cover evaluator, simulator, variants, and explanation logic only. There are no DOM, visual, or accessibility tests for theme focus states.

suggested regression test:
Add a browser smoke test that cycles through each theme, tabs through visible controls, and asserts focused buttons have a visible focus indicator such as non-none outline, border change, or focus box-shadow.

minimum fix scope:
themes/vegas-neon.css button focus styling.

repro:
Switch to Vegas Neon and tab to Deal, Play, or Fold. The theme sets button outline to none and adds no button-specific focus-visible border, outline, or shadow.
